# Upgrade Script — projects 4.2.x → 4.3.0

**MINOR migration. Recommended, not required.** 4.3 fixes a defect in 4.2's handling of projects that already had action items, and offers to reserve the ID prefixes your projects are already using. Everything this script does also happens on its own, project by project, the next time a member creates an action item — this is the bulk version, run once by an admin.

## What 4.2 got wrong

4.2 assumed a project without a recorded prefix had been issuing `AI-001`-style IDs, because `AI-` was the hardcoded prefix in 4.1. In practice, projects were already using their own conventions — `AC-`, `AW-`, `CI-`, bare integers — because members had been hand-rolling prefixes, which is what motivated the feature.

Two consequences on 4.2, both fixed in 4.3:

1. **Sequence splitting.** A project on `AC-040` would issue `AI-041` next, and the prefix lock then made the split permanent.
2. **Prefix theft.** Prefixes already in use held no registry claim, so a new project could be told `AC` was free, claim it, and mint a second `AC-001`.

**Nothing that already exists is rewritten.** Item IDs are never renumbered to add or change a prefix. A project whose items predate any convention keeps them exactly as they are, permanently. If some of your IDs are out of compliance with the current scheme, they stay out of compliance — that is deliberate.

## Before you start

- Upgrade to 4.3.0 first (`@ai:update`).
- Run this **before** `@ai:install-collection projects` applies provisioning, so prefixes are reserved before anything can claim from the registry.
- Have a view on projects whose ID shape is ambiguous — you will be asked to decide. You may consult the project owners or not; that is your call, and deliberately not something this script assumes.

## Admin half — projects you can see

For every project in `/shared/projects-index/`, the script resolves where that project's content actually lives, reads its existing action items, works out the prefix in use, and **presents it for you to accept, override, or skip**.

**Where the content lives is read from the pointer, never assumed.** A pointer with `location.path` means the commons; one with `location.folder_id` means the owner's own drive (opened cross-drive via `item_drive_id` when present). Assuming `/shared/projects/{slug}/` is wrong for any project that has ever been transitioned private — going private leaves a stub, `{"moved": true}`, at the old commons path, and reading that would report "no items in use" while the real project has items and an unreserved prefix.

Three empty-looking states mean different things and are not treated alike: **no file** (never had items), **an empty list** (genuinely empty), and **a stub** (content is somewhere else — follow the pointer).

```
access-control      uses AC   (40 items, next would be AC-041)   [accept / override / skip]
agency-workflow     uses AW   (3 items)                          [accept / override / skip]
some-project        bare integers - no prefix in use             [choose / skip]
other-project       mixed stems: XX (4 items), YY (2 items)      [choose / skip]
legacy-project      items: [] but next_id 12 - IDs were issued
                    and removed; no stem recoverable             [choose / skip]
```

**Nothing is guessed.** Where the in-use prefix is unambiguous you are shown it and can accept with a keystroke; where it is not, you decide.

On **accept** or **override**, for that project:
1. The prefix is claimed at `/shared/prefix-registry/{PREFIX}.json`, carrying the **project owner's** member hash — *not yours*. Running this upgrade is an administrative act; it does not make you the owner of anything.
2. `action_item_prefix` is recorded in the project's `project.md` and its discovery pointer.

On **skip**, nothing is written. That project is covered later by the inline offer when someone next adds an item to it.

**Conflicts do not stop the run.** If a prefix is already claimed by a different project, that project is reported and skipped, and the pass continues. Neither project can be renumbered, so resolving it is a human decision — see "If two projects share a prefix" below.

**Re-runnable.** Running it again presents only the projects still unclaimed. Once everything is reconciled, re-running it is the standing audit: it compares every project's recorded prefix against the registry's owner and reports any mismatch.

## Projects you can see but cannot read

Some projects are private but **shared** — they have a pointer, so you can see they exist, but their content sits in the owner's drive and only their grantees can read it.

**The script decides this from the pointer, before it tries to read anything.** If the pointer's `scope` names readers and collaborators rather than saying `org_public`, and you are neither the owner nor named in it, the project is classified as the owner's to handle and is never opened.

That ordering is deliberate. If you have no grant on a folder, the backend does not tell you so — it tells you the folder is not there. `exists` comes back false, a listing comes back empty, and a read comes back "file not found", none of them as an error, and all of them identical to what a genuinely empty project returns. A script that read first and drew conclusions would report "nothing to reconcile" for a project that has forty action items and an unreserved prefix. So it checks the pointer, which does know, instead of the folder, which cannot say.

If you are not a grantee, the script reports:

```
pj-private-one      visible, not readable - the owner handles this      [no action]
```

That is not a failure and not a skip-in-silence. You have no standing to reserve a prefix for content you cannot see, and the owner is covered automatically the next time they add an action item.

## Private projects — not reachable from here

Projects that have never been shared have no pointer at all and are invisible to an admin by design, so this script cannot see, read, or reconcile them. Their owners are covered two ways:

- The inline offer when they next create an action item in that project.
- A one-time session-start mention: *"{N} of your private projects haven't claimed their action-item prefix."*

You do not need to chase anyone. If you want to, that is your process choice.

## Also corrected

If your org was provisioned under 4.2, `/shared/prefix-registry/README.md` says entries are "never deleted". That is wrong — there is exactly one case where an entry is removed: releasing a superseded prefix after its replacement has been confirmed. This script rewrites that file.

## If two projects share a prefix

Possible in any org that predates 4.2, because nothing enforced uniqueness. Both projects' IDs are already in circulation and **neither can be renumbered**, so there is no automatic resolution. The script reports both and moves on. Your options are to leave them (accepting that `AC-007` is ambiguous across two projects), or to have one project adopt a new prefix going forward — which splits its sequence deliberately rather than accidentally, and is a decision for its owner.

## When you are done

- Every project you accepted holds a registry claim owned by its owner, and records its prefix.
- Skipped and private projects still work: they keep issuing the IDs they already issue, and get the inline offer later.
- No action item, anywhere, has changed.
